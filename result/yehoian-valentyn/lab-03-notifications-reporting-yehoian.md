## 0. Вихідні дані й огляд артефактів

Модуль Notifications / Reporting для «КавоХаб» споживає події CRM, Orders, Inventory та Billing, веде локальні репліки й журнал, формує оперативні звіти та надсилає листи через outbox-worker. Odoo використовується як бухгалтерське джерело; Notifications читає PDF/дані рахунку, а створення й проведення рахунку належать Billing.

| ADR-0005 | [ADR-0005-email-unavailable-notifications.md](ADR-0005-email-unavailable-notifications.md) | Запропонована поведінка при збоях пошти, автоматичні повтори й наслідки |

**Вихідні рішення з ЛР2:** окремий Notifications-сервіс; Odoo — бухгалтерське джерело; `inventory.shipment.dispatched` запускає лист із ТТН і дає умову для відправлення PDF-рахунку; модель `Notification` має стани `waiting`, `pending`, `sending`, `retry_wait`, `sent`, `final_failed`, `suppressed`.

### OpenAPI та робота з mock

Контракт містить `/health`, журнал і деталі сповіщень, admin-only `resend`, щоденний звіт, звіт неактивних орендарів і метадані шаблонів. Успішні відповіді — JSON, помилки — `application/problem+json`; кожна відповідь містить `X-Correlation-Id`. Для `resend` потрібні bearer JWT і UUID `Idempotency-Key`.

Правила контракту: kebab-case і множина для ресурсних шляхів (винятки `/health` і дія `/resend`); camelCase у JSON; дати-часи RFC 3339 у UTC; `Problem` для помилок; `page >= 1`, `1 <= pageSize <= 100`. Споживачі запускають mock на основі `openapi.yaml` (наприклад, Prism), перевіряють приклади успіху й помилок, а потім запускають контрактні перевірки проти реального провайдера за тими самими схемами.

### Версіонування контрактів

Поточний AsyncAPI контракт має версію `1.0.0`. Додавання необов'язкового поля — сумісна зміна; додавання обов'язкового поля, видалення/перейменування поля або звуження enum — потенційно несумісна зміна, що потребує погодження споживачів і нової major-версії контракту. Зміна `orders.order.confirmed` із новими обов'язковими полями лишається вимогою до команди Orders і не вважається прийнятою їхньою командою до погодження.

## 1. RabbitMQ: топологія й ідемпотентний consumer

Exchange `kavohub.events` — durable topic. Notifications споживає бізнес-події з основної черги, retry-черги та окрему чергу DLQ-алертів. DLQ-алерт створює модуль-власник DLQ і публікує його за routing key `dlq.alert`; Notifications не читає DLQ інших модулів напряму.

| Об'єкт | Параметри / призначення |
|---|---|
| Exchange | `kavohub.events`, `topic`, durable |
| Основна черга | `notifications.events`, durable; bindings: `crm.deal.won`; `orders.order.confirmed`, `orders.order.cancelled`; `inventory.stock.reserved`, `inventory.stock.reservation_failed`, `inventory.shipment.dispatched`; `billing.invoice.issued`, `billing.payment.received` |
| Retry-черга | `notifications.events.retry`, durable; TTL `5000 ms`; після TTL dead-letter routing key повертає повідомлення до `notifications.events` |
| DLQ | `notifications.events.dlq`, durable; отримує п'яту невдалу обробку та невалідні/нерозбірливі повідомлення |
| DLQ-алерти | routing key `dlq.alert` у виділений канал; черга Notifications `notifications.dlq-alerts` |
| Consumer | `prefetch=10`; ACK лише після commit бізнес-транзакції або після publisher confirm копії в retry/DLQ |
| Лічильник | `x-retry-count` починається з `0`; інкрементується під час підтвердженої публікації в retry; п'ять загальних спроб включають першу |

|---|---|---|---|

| `billing.payment.received` | Оновити звіт; повідомити менеджера, без клієнтської квитанції | Event ID; `paymentId` для фінансової зміни | Менеджер з order replica; за відсутності — директор із записом fallback |

### Синхронні стики

| Стик | Операція / тайм-аути | Повтори й ідемпотентність | При недоступності |
|---|---|---|---|
| Notifications → Odoo | Read-only отримання PDF за `invoiceId`/`pdfRef`; timeout треба підтвердити на цільовій інсталяції | До 3 спроб загалом з інтервалом 5 хв; окремий `pdfFetchAttemptCount`; read є безпечною операцією | Не відправляти лист без PDF; після третьої невдачі `final_failed` та ІТ-алерт |
| Outbox worker → SMTP | Connect timeout 5 с; send timeout 30 с | До 3 спроб загалом; 5 хв після завершення попередньої, jitter ±10%; provider idempotency не підтверджена | Тимчасова помилка → `retry_wait`; auth/config → пауза без збільшення лічильника; permanent address error → `final_failed` |

Для вихідних викликів worker записує `correlationId` у структурований лог. `Idempotency-Key` в OpenAPI стосується лише admin-команди `POST resend`; модуль не має синхронних POST-викликів до Orders/Billing.

Після п'ятої невдачі consumer публікує повідомлення в DLQ і чекає publisher confirm; лише потім ACK-ає оригінал. Невалідна схема/нерозбірливий payload іде в DLQ без п'яти повторів. DLQ-запис містить оригінальне тіло, routing key, заголовки й причину; email маскується. Повторна ручна доставка ІТ збільшує `incidentCycle`.

Для власної `notifications.events.dlq` Notifications сам створює внутрішнє ІТ-сповіщення; цей алерт не публікується на шину.

### Ідемпотентний споживач

```sql
CREATE TABLE notifications.processed_events (
  source       text        NOT NULL,
  event_id     text        NOT NULL,
  event_type   text        NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (source, event_id)
);
```

```text
отримати повідомлення m
BEGIN
  вставити (m.source, m.id, m.type) у processed_events
  якщо конфлікт ключа: COMMIT; ACK; завершити (дубль)
  застосувати бізнес-зміну та оновити репліку
  створити Notification/outbox за ключем
    triggerOccurrenceId + recipientId + notificationType
COMMIT
ACK оригіналу

при тимчасовій помилці:
  ROLLBACK
  якщо це спроби 1–4: опублікувати retry із x-retry-count + 1;
    ACK оригіналу лише після publisher confirm
  якщо це спроба 5: опублікувати в DLQ;
    ACK оригіналу лише після publisher confirm
```

Падіння між commit та ACK призводить до redelivery; унікальний `(source,event_id)` перетворює його на безпечний дубль. Лист не надсилається всередині RabbitMQ-транзакції: outbox-запис фіксується разом із бізнес-зміною, а окремий worker надсилає email.

### Сценарії RabbitMQ: дія та підтвердження

| Сценарій | Дія | Черга | ACK/NACK оригіналу |
|---|---|---|---|
| Успішна обробка | Транзакційно записати event, бізнес-зміну та outbox; commit | `notifications.events` | ACK після commit |
| Дубль | Знайти `(source,event_id)`, не повторювати side effect | `notifications.events` | ACK після перевірки дубля |
| Тимчасова помилка, спроби 1–4 | Публікувати retry з інкрементованим `x-retry-count`; чекати confirm; TTL 5 с повертає в основну чергу | `notifications.events.retry` → `notifications.events` | ACK лише після publisher confirm; інакше лишити непідтвердженим |
| П'ята невдача | Публікувати збережене повідомлення та причину в DLQ; чекати confirm | `notifications.events.dlq` | ACK лише після publisher confirm |
| Невалідна схема | Не застосовувати бізнес-зміну; зберегти тіло, headers і причину в DLQ | `notifications.events.dlq` | ACK лише після publisher confirm |
| БД недоступна | Rollback; за доступного брокера повторити до 5 загальних спроб; після п'ятої — DLQ | Retry → DLQ | ACK після confirm retry/DLQ; до того не ACK-ати |
| Commit відбувся, ACK загубився | Redelivery; `processed_events` виявляє дубль | `notifications.events` | Повторний delivery ACK-ується без side effect |
| Брокер недоступний при retry-публікації | Не ACK-ати оригінал; після відновлення відновити доставку, publisher confirm і лічильник | Оригінал лишається непідтвердженим; далі retry/DLQ | Не ACK/NACK-ати з негайним requeue; публікацію підтвердити після відновлення |

П'ять спроб із TTL 5 с займають близько 20–25 секунд лише поки broker доступний для циклів retry/DLQ. Якщо недоступний сам RabbitMQ, публікацію в retry/DLQ підтвердити неможливо, тож повідомлення лишається непідтвердженим до відновлення.

## Сценарії стійкості (Given / When / Then)

### RES-01 — Пошта недоступна 10 хвилин

- **Given:** сповіщення готове до надсилання, SMTP тимчасово недоступний.
- **When:** worker робить до трьох спроб загалом; інтервал — 5 хвилин від завершення попередньої спроби з jitter ±10%.
- **Then:** якщо SMTP відновився до успішної спроби, лист надсилається; якщо всі три спроби невдалі, сповіщення переходить у `final_failed` та створюється ІТ-алерт із ключем `final-failure + notificationId + deliveryCycle`. Для мертвої пошти основні канали ІТ — метрика й лог.
- **Стан:** `retry_wait` між спробами, потім `sent` або `final_failed`.
- **Бачить клієнт:** лист не надходить до успішного надсилання.
- **Бачить оператор:** стан і спроби в журналі; email отримувача замаскований. За системної помилки автентифікації/конфігурації — метрика й лог, worker на паузі, лічильник спроб не змінюється.

### RES-02 — Odoo недоступний, PDF рахунку немає

- **Given:** відвантаження вже підтверджене, але PDF рахунку з Odoo недоступний.
- **When:** адаптер Notifications робить до трьох спроб отримання PDF загалом із п'ятихвилинним інтервалом; цей лічильник окремий від SMTP.
- **Then:** після отримання PDF починається окремий SMTP-цикл; після трьох невдалих спроб PDF-сповіщення переходить у `final_failed`, створюється ІТ-алерт, лист без PDF не надсилається.
- **Стан:** `retry_wait` під час повторів отримання PDF; далі `pending` перед SMTP-відправленням або `final_failed`.
- **Бачить клієнт:** не отримує листа без вкладення.
- **Бачить оператор:** причину недоступності PDF і окремий лічильник спроб Odoo; SMTP-спроби починаються лише після отримання PDF.

### RES-03 — RabbitMQ недоступний під час retry-публікації

- **Given:** обробка події завершилася тимчасовою помилкою, а retry-публікація не отримала publisher confirm.
- **When:** RabbitMQ недоступний, а згодом відновлюється.
- **Then:**
  1. Поки брокер не підтвердив retry-публікацію, consumer не ACK-ає оригінал; після втрати з'єднання повідомлення лишається непідтвердженим і буде доставлене повторно після відновлення.
  2. Після відновлення брокера повторні невдалі обробки проходять за політикою до п'яти загальних спроб із retry TTL 5 с; п'ята невдача спрямовує повідомлення до DLQ, а оригінал ACK-ується лише після publisher confirm DLQ-публікації.
  3. Після відновлення залежностей ІТ вручну виконує requeue; новий інцидент має збільшений `incidentCycle`.
- **Стан:** до commit нового сповіщення немає, наявний стан не змінюється; після п'ятої невдалої обробки подія перебуває в DLQ.
- **Бачить клієнт:** листа немає до успішної обробки події та доставки через outbox.
- **Бачить оператор:** спершу помилку/відсутність confirm; після потрапляння в DLQ — алерт, причина й `incidentCycle`.

> П'ять спроб займають орієнтовно 25 секунд лише коли брокер доступний для циклів retry/DLQ. Під час повної недоступності RabbitMQ неможливо підтвердити публікацію до retry або DLQ; відлік спроб триває після відновлення брокера.

### RES-04 — БД недоступна під час обробки події

- **Given:** consumer отримав подію, але БД недоступна.
- **When:** транзакція не може зафіксувати `processed_events`, бізнес-зміну й outbox-запис.
- **Then:** транзакція відкочується; за доступного RabbitMQ подія проходить до п'яти загальних спроб із TTL 5 с і після п'ятої невдачі потрапляє в DLQ. Після відновлення БД ІТ вручну виконує requeue, збільшуючи `incidentCycle`.
- **Стан:** нового сповіщення немає, бо транзакція не commit-нулась; раніше зафіксований запис зберігає останній commit-нутий стан.
- **Бачить клієнт:** листа немає до успішної обробки події та подальшого надсилання.
- **Бачить оператор:** помилки БД у метриці/логу; після DLQ — алерт і цикл інциденту. П'ять спроб вичерпуються приблизно за 25 секунд за доступного брокера.

### RES-05 — Дубль події

- **Given:** подія з тим самим `(source, event_id)` вже оброблена й зафіксована.
- **When:** consumer отримує її повторно.
- **Then:** бізнес-зміна й outbox-запис не дублюються; подія ACK-ується. Дедуплікація сповіщення додатково використовує `triggerOccurrenceId + recipientId + notificationType`.
- **Стан:** стан наявного сповіщення не змінюється.
- **Бачить клієнт:** одне логічне сповіщення; фізичний дубль можливий за невизначеного результату SMTP (RES-10).
- **Бачить оператор:** один запис сповіщення; повтор можна побачити в журналі/метриці обробки подій.

### RES-06 — Рахунок надійшов раніше за відвантаження

- **Given:** `billing.invoice.issued` надійшла раніше за `inventory.shipment.dispatched`.
- **When:** Notifications зберігає рахунок в очікуванні за `orderId`.
- **Then:** якщо відвантаження надійшло в межах 24 годин — очікування завершується й починається окремий процес отримання PDF; якщо ні — сповіщення переходить у `suppressed`, тайм-аут записується в журнал. 24-годинне очікування відвантаження не витрачає ліміт спроб отримання PDF.
- **Стан:** `waiting` до відвантаження; потім `pending`/`retry_wait` для PDF або `suppressed` після 24 годин.
- **Бачить клієнт:** не отримує листа до відвантаження; потім отримує його лише з доступним PDF. Після тайм-ауту листа немає.
- **Бачить оператор:** `waiting`, далі стан отримання PDF або `suppressed` із причиною тайм-ауту.

### RES-07 — Збій після commit, але до ACK

- **Given:** транзакція зафіксувала подію в `processed_events`, бізнес-зміну й outbox-запис.
- **When:** consumer падає до ACK і RabbitMQ доставляє подію повторно.
- **Then:** повтор знаходить `(source, event_id)`, не створює другу бізнес-зміну/outbox-запис і ACK-ується; outbox-worker продовжує доставку окремо.
- **Стан:** зберігається останній стан, зафіксований у БД; outbox-worker може просунути його далі.
- **Бачить клієнт:** одне логічне сповіщення після доставки; невизначене підтвердження SMTP може спричинити фізичний дубль.
- **Бачить оператор:** один запис сповіщення й outbox; повторна подія не створює повторної бізнес-зміни.

### RES-08 — SMTP auth/config помилка

- **Given:** worker отримує системну помилку автентифікації або конфігурації SMTP.
- **When:** помилка виявлена до підтвердженого прийняття листа.
- **Then:** worker призупиняє відправлення; лічильник SMTP-спроб не збільшується. Метрика й структурований лог — основні канали; ІТ-лист створюється/надсилається за можливості. Після усунення помилки worker відновлює outbox-обробку.
- **Стан:** повідомлення лишається в `retry_wait` або `pending` до відновлення worker; спроба не зараховується.
- **Бачить клієнт:** лист не надходить до відновлення SMTP.
- **Бачить оператор:** системну помилку в метриці й логах; ІТ-лист — якщо поштовий канал доступний.

### RES-09 — Невалідна email-адреса

- **Given:** SMTP повертає постійну помилку, яка підтверджує невалідну адресу отримувача.
- **When:** worker класифікує адресу як `permanent_failure`.
- **Then:** автоматичні повтори не виконуються; сповіщення переходить у `final_failed`, для звичайного сповіщення створюється ІТ-алерт з ключем `final-failure + notificationId + deliveryCycle`.
- **Стан:** `final_failed`.
- **Бачить клієнт:** лист не надходить.
- **Бачить оператор:** `final_failed`, код постійної помилки та замасковану адресу; повтор потребує виправлення адреси й дозволеної admin-дії.

### RES-10 — Провайдер прийняв лист, але підтвердження загубилося

- **Given:** поштовий провайдер прийняв лист, але worker не отримав підтвердження результату.
- **When:** спроба завершується тайм-аутом і класифікується як `transient_failure`.
- **Then:** якщо ліміт не вичерпаний, створюється наступна SMTP-спроба за політикою ADR-0005; після третьої невдалої спроби — `final_failed`. Повтор може створити фізичний дубль, бо ідемпотентність провайдера не підтверджена.
- **Стан:** `retry_wait` до наступної спроби або `final_failed` після вичерпання трьох спроб; `sent` лише за підтвердженого результату.
- **Бачить клієнт:** може отримати лист один раз або дубль; гарантовано визначити результат до повтору неможливо.
- **Бачить оператор:** спробу з `transient_failure`, факт невизначеного результату та можливий ризик дубля в журналі.

Для всіх повідомлень конверт має `specversion`, `id`, `type`, `source`, `time`, `correlationId`, `data`. `correlationId` має проходити від угоди до платежу. Споживачі дедуплікують події за `(source, event.id)`; повідомлення — за `triggerOccurrenceId + recipientId + notificationType`. Учасники обробляють події асинхронно, тому порядок `invoice.issued` і `shipment.dispatched` може відрізнятися від лінійного happy path; `orderId` дозволяє зберегти рахунок в очікуванні відвантаження.

### Рецензія прогону

- У лінійному happy path бракувало перевірки резерву: клієнтське підтвердження надсилається лише після `stock.reserved`, отриманого не пізніше 15 хв від `orders.order.confirmed`. Після тайм-ауту листа клієнту немає, створюється ІТ-алерт за `orderId + version`; `reservation_failed` скасовує таймер без timeout-алерту.
- Гілка скасування замовлення не входить у цей happy path: якщо підтвердження вже доставлено, клієнтці повідомляють про скасування; якщо shipment уже відбувся — повідомляють менеджера замість клієнтки.
- `billing.invoice.issued` може прийти раніше за `inventory.shipment.dispatched`. Notifications має зберегти рахунок за `orderId`, не відправляти його передчасно й застосувати окрему 24-годинну умову очікування shipment.
- `billing.payment.received` оновлює звіт і надсилає лист менеджеру; квитанція клієнтці не надсилається. Якщо менеджера немає в репліці, лист отримує директор, а fallback записується в журнал.
- Odoo тут є джерелом PDF/бухгалтерських даних для Notifications; операції створення й проведення рахунку належать Billing. Сервісний доступ Notifications до Odoo — read-only.
- `delivery_status_changed` лишається поза межами ЛР3; повний happy path не перевіряє статус доставки після відвантаження.

## Відповіді на контрольні питання

1. **Навіщо contract-first?** Контракт фіксує поля, помилки й поведінку до реалізації; споживач може інтегруватися з mock-сервером, а провайдер перевіряє реальну відповідь тією самою схемою.
2. **Чим OpenAPI відрізняється від AsyncAPI?** OpenAPI описує синхронні HTTP-операції REST API; AsyncAPI описує повідомлення, канали (тут routing keys RabbitMQ) та операції споживача `receive`.
3. **Чому ACK після commit?** Якщо ACK зробити раніше, а процес упаде до commit, подія буде втрачена для бізнес-обробки. Commit спершу дає повторну доставку після збою; `processed_events` перетворює її на безпечний дубль.
4. **Як обробляється дубль події?** Унікальний `(source,event.id)` не дозволяє вдруге застосувати зміну або створити outbox; consumer ACK-ає дубль. Ключ сповіщення окремо обмежує повторне створення листа.
5. **Які помилки повторюються?** Тимчасові помилки SMTP повторюються до трьох спроб загалом; невалідний email завершується `permanent_failure`. SMTP auth/config призупиняє worker без витрати спроб. RabbitMQ-транспортні повтори мають окремий ліміт п'ять.
6. **Що робить Notifications з рахунком раніше shipment?** Зберігає його за `orderId` у `waiting` максимум 24 години. До відвантаження не надсилає лист; після shipment отримує PDF окремими трьома спробами. Без shipment після тайм-ауту — `suppressed` і запис у журнал.
7. **Як обробляється збій пошти на 10 хвилин?** Outbox зберігає лист; worker робить до трьох загальних SMTP-спроб із п'ятихвилинним інтервалом і jitter. Якщо всі невдалі — `final_failed`, ІТ-алерт за циклом; при мертвій пошті основними сигналами є метрика й лог.
8. **Яку розбіжність знайдено в Lead-to-Cash?** Подія CRM містить `dealId/accountId/ownerId`, але Orders має додати ці поля до `orders.order.confirmed`, щоб Notifications могла вести репліку `orderId → dealId, accountId, ownerId` і адресувати листи.

## Робота з ШІ-асистентом

- Перевірено й виправлено форму OpenAPI Problem Details та приклади; окремо валідували приклади OpenAPI/AsyncAPI за їхніми схемами.
- Розділено RabbitMQ retry (5 загальних спроб) і SMTP retry (3 загальні спроби), а також PDF fetch retry як окремий лічильник.
- Уточнено, що Notifications лише читає Odoo для PDF; створення/проведення рахунку залишається відповідальністю Billing.
